# App records

One folder per app that was onboarded (or attempted), containing the **exact** workflow
that was generated and a written record of how it was debugged. This is the reference
library for "how did we make this app build?", not a second template.

```
apps/
  <id>/
    meta.yml                 # machine-readable facts (status, tag, sizes, decisions)
    build-app-bundle.yml     # byte-for-byte copy of the generated workflow
    patch.R                  # only if the app used PATCH_SCRIPT
    NOTES.md                 # why it is packaged this way + the debug log
  INDEX.md                   # generated by scripts/build-app-index.ps1
  _template/                 # starters for a new record
```

## Status

`meta.yml` `status` describes **build and authorization state**. Whether an app is
actually installable is decided by `ShinyApps/catalog/apps.yml` -- the catalog is the
single source of truth and this folder is only a snapshot.

| status | Meaning |
|---|---|
| `active` | in the catalog and buildable |
| `pending` | bundle builds; not in the catalog (author decision pending, or user testing) |
| `rejected` | the author declined. **Do not redistribute**; keep only as a reference |
| `withdrawn` | was listed, removed on request/decision |
| `abandoned` | never produced a usable bundle; kept for the failure record |

If the catalog and a record disagree, the catalog wins: update the record's `status`, do
not edit the catalog from here.

## What is stored, and what is not

Stored: the generated workflow **at the release tag** (placeholders already substituted,
so it is exactly what ran), the values that differ from the template, and the reasoning.
Optional: the `PATCH_SCRIPT` file.

Not stored: bundles, `rlib/`, `deps-*.json`, tokens, or local absolute paths. Link the
Release and the Actions run in `meta.yml` instead.

## Snapshot, not mirror

`build-app-bundle.yml` is **immutable**. It is the file that produced the release, pinned by
`workflow_sha256`, `workflow_commit` and `tag`. Do not overwrite it when the fork changes:
that would erase the evidence. Instead:

- `scripts/record-app.ps1` snapshots a new release (workflow at the tag, assets, SHAs);
- `scripts/check-upstream.ps1` compares the fork's current workflow and upstream code with the
  snapshot and reports `workflow-drift` / `rebuild` / `sync-first` in `site/status.json`;
- a weekly workflow publishes that report to the maintenance board (GitHub Pages).

If a workflow change should be shipped, bump the tag and record the new release. The old
snapshot stays in git history.

## Special package versions

`pkg-versions.tsv` reserves app-unique numeric suffixes for packages that are patched per
app (Cairo with vendored XQuartz dylibs, etc.). The shared library deduplicates by package
name+version, so identical versions can overwrite each other. Allocate with
`scripts/next-pkg-version.ps1` and read `references/special-packages.md` before adding an
app that vendors such a package.

## Provenance fields

`meta.yml` records `built_at` (release `published_at`), `source_repo` / `source_commit`
(tag commit), `upstream_repo` / `upstream_head` (observed at record time),
`workflow_path` / `workflow_commit` / `workflow_sha256`. The validator recomputes the hash,
so an edited snapshot is caught.

## Adding a record

```powershell
.\scripts\new-app-record.ps1 -AppId <id> -Name "<Name>" `
  -Upstream <owner>/<repo> -Fork <owner>/<repo> -License <SPDX> `
  -Platforms "win-x64, mac-arm64" -Tag v0.1.0 `
  -WorkflowPath <path-to-generated-workflow.yml>
```

For a released bundle use the recorder instead of copying by hand (it pulls the workflow at
the tag, the asset sizes and the SHAs):

```powershell
.\scripts\record-app.ps1 -AppId <id> -Fork <owner>/<repo> -Upstream <owner>/<repo> -Tag v0.1.0
```

Add `-Status active` when the app is already in the catalog, and `-Force` when replacing an
older snapshot of the same app with a newer release.

Then fill `meta.yml` `decisions:` and `NOTES.md` (why each non-default value is set, plus
the debug log), run the validator, and regenerate the index:

```powershell
.\scripts\validate-apps.ps1
.\scripts\build-app-index.ps1
.\scripts\validate-apps.ps1 -CatalogPath <path-to-ShinyApps/catalog/apps.yml>
```

Manual route: copy `_template/` to `apps/<id>/`, fill it in, and copy the workflow from
the fork (take it from the **tag**, not from `main`, so it matches the published bundle).

## Reusing a record

The `env:` block is app-specific: copy the structure and the *reasoning*, then redo the
dependency census for the new app. Never copy `APP_ID`, asset names, or `APP_NOTES`
verbatim. Public records must stay free of tokens, private URLs, and author machine paths.
